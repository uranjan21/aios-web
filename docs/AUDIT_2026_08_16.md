### What BYOK looks like now
- `user_api_keys` — Fernet-encrypted with `TOKEN_ENCRYPTION_KEY`, unique per (user, provider), CASCADE on user delete.
- `app/services/ai/keys.py` — the only place a credential is resolved. **No instance-key fallback, deliberately.**

- Interactive paths return **428** `{"error":"no_api_key","provider":…}`; background jobs degrade to facts-only and never raise.
- `TOKEN_ENCRYPTION_KEY` is now a hard production boot guard. **It is a single point of data loss — rotate it and every user must re-enter their key.**

### 🔴 A data-destroying migration was caught before it ran
The first draft of `m002_enum_checks` normalised rows outside its allowed set:
`UPDATE <table> SET <col> = <fallback> WHERE <col> NOT IN (...)`.
Two of its value sets did not match reality:
- **`finance_accounts.type`** is a native Postgres ENUM storing member NAMES (`'CHECKING'`), not the lower-case values the constraint listed. **All 17 accounts would have been rewritten to one type.** The column is now excluded entirely — the enum type is already the guard.
- **`finance_investments.type`** held `bond`, `fixed_deposit`, `retirement` in live data, none of which were in the allowed set. **Those rows would have been flattened to `mutual_fund`.** Set widened to match reality.

The normalisation now touches **NULLs only** and **raises** on any other out-of-set value rather than guessing, with a message telling the operator to widen the tuple instead of rewriting data. Verified by cloning the real database, applying the whole chain, and confirming all 17 account types and all 9 investment types survived byte-for-byte.

### Other real bugs found while finishing
- **`/api/ai/skill-gap` was a guaranteed 500** — `SkillInventory.user_id == str(current_user.id)` against a UUID column (`AttributeError: 'str' object has no attribute 'hex'`). Pre-existing; exposed by the new BYOK tests.
- The test suite's `TOKEN_ENCRYPTION_KEY` was base64 text but **not a valid Fernet key** — harmless while it was only decorative, fatal once real secrets used it.

### Deliberately NOT done, with reasons
- **S17 soft delete** — designed, not implemented. It touches every financial handler and is a product decision; a design note was written instead of a half-applied version.
- **S12 mixed naive/aware timestamps** — investigated, deferred. The original conversions ran without `USING … AT TIME ZONE 'UTC'`, so a blind fix risks shifting historical values. A correct write-up beat a data-corrupting migration.
- **F2 form validation** — advanced from ~11 to **66 validated field sites across 23
  files**; `toast.error` fell 175 → 147 as input errors moved onto the fields that
  caused them. Against 168 `<Input>` renders this is roughly 40% coverage: every

  long tail of single-field and settings forms is not. `useFieldErrors` now lives
  once in `@ct/shared` and is memoised — it previously returned a fresh object each
  render, silently defeating every consumer's dependency array.

## Verdict

**NO-GO for paying customers.** Not because the application is bad — the isolation
backbone is genuinely intact, all gates that exist are green, and the config-guard
discipline is well above average. It is a **NO-GO on operability and on a handful of
correctness landmines**:

1. You cannot detect a production incident (no error tracking, no uptime check, no alerting).
2. You cannot recover from losing the box (backups live on the DB's own disk, never restore-tested).
3. A config landmine silently breaks auth for half of all requests under >1 worker.
4. Metered AI usage is permanently destroyed on any Stripe failure — direct revenue loss.

These are small, bounded fixes. Realistically **one focused day** clears the launch
blockers; the quality tail behind them is 3–4 weeks.

# PHASE 0 — Launch blockers (target: 1 day)

Nothing else in this document matters until these four are done.

- [ ] **B1 · `APP_SECRET_KEY` random default defeats the production guard** [V]
  `backend/app/core/config.py:13` — `Field(default_factory=lambda: secrets.token_urlsafe(32))`.
  The prod validator (`config.py:121`) rejects `_INSECURE_DEFAULTS` or `<32 chars`; a
  generated 43-char key passes both. `backend/Dockerfile:71` runs gunicorn **without
  `--preload`**, so each of `WEB_CONCURRENCY` workers imports the app and gets its *own*
  key. A JWT minted by worker A is rejected by worker B → **~50% of authenticated
  requests 401 at random**, and every restart signs out every user. Invisible in logs.
  *Fix:* `app_secret_key: str = ""` + `if not self.app_secret_key: raise` in the
  production branch. Add the unset-var case to `tests/test_config_guards.py` — it
  currently proves the stated guards fire, not that an **unset** var is caught.

- [ ] **B2 · No way to know production is broken**
  Backend Sentry is wired (`app/core/observability.py:35`) but `SENTRY_DSN=` is empty in
  `.env.prod.example:126`. Frontend Sentry/PostHog are build-arg-only and resolve to `""`
  by documented default. No `/metrics` endpoint exists. Logs are good (JSON + request ids)
  but trapped on-box behind a `10m × 3` rotation (`docker-compose.prod.yml:26`). The
  Caddyfile comment says `/health` is proxied "so an external uptime monitor can hit it" —
  **no monitor is configured anywhere.**
  *Fix (<1h):* set `SENTRY_DSN` + `VITE_SENTRY_DSN` (+ the ingest host in
  `CSP_CONNECT_EXTRA`), and point a free external uptime check at `/health` with
  email/SMS alerting.

- [ ] **B3 · Backups are on the database's own disk and have never been restored**
  `deploy/deploy.sh:65` `resolve_backup_dir()` prefers `/var/backups/control-tower`, falls
  back to `$APP_DIR/backups` — the script's own comment concedes this is weak. Nothing
  copies dumps off-box. **Real RPO/RTO if the VPS disk is lost — the exact scenario
  backups exist for — is ∞/∞.** Customer financial and health data would be gone
  permanently.
  *Fix:* add an `rclone`/`aws s3 cp` step to `deploy/backup-db.sh`; then perform **one
  timed restore** into a scratch container to establish a real RTO number and prove the
  dumps are valid.

- [ ] **B4 · Redis is a total-outage SPOF that also poisons deploy rollback**
  `backend/app/core/rate_limit.py:31` builds `Limiter(storage_uri=redis_url)` with
  slowapi's defaults — `swallow_errors=False`, no in-memory fallback [V]. Storage errors
  re-raise → every rate-limited endpoint 500s. `/health` is itself rate-limited
  (`main.py:240`), so Redis dying makes `deploy.sh wait_healthy()` fail and the **next
  deploy rolls back for the wrong reason** while the app is 100% down.
  ⚠️ `docs/PRODUCTION_RUNBOOK.md:113-120` documents the **opposite** behaviour
  ("fail-open") — that is true only of the WebSocket path (`api/chat.py:149`), not HTTP.
  On-call will debug the wrong thing.
  *Fix:* `Limiter(..., in_memory_fallback_enabled=True)`, drop the limiter from `/health`,
  and correct the runbook.

# PHASE 1 — Correctness & revenue (target: week 1)

- [ ] **B5 · Metered AI usage is marked billed even when Stripe reporting failed** [V]
  `backend/app/services/billing/usage.py:163` — after a loop that `continue`s past every
  failure, `for r in rows: r.reported_to_stripe = True` flips **all** rows
  unconditionally. A Stripe outage, a missing `ai_usage` line item, or a failed
  subscription lookup means that usage is **permanently unbillable**, with no retry and
  no dead-letter. Direct revenue loss on the metered half of the pricing model.
  Secondary: the driving `select` (`:114`) has **no LIMIT** and is global across tenants.
  *Fix:* collect `reported_user_ids` inside the loop; only flip rows whose `user_id` is in
  that set. Treat "no subscription to bill to" as a distinct state, not as billed.

- [ ] **D1 · Deleting a finance account 500s whenever it has any history** [V]
  `backend/app/api/areas/finance.py:1402` is a bare `db.delete(account)`. **Eleven** tables
  carry `account_id → finance_accounts.id` with **no `ondelete`**. The only realistic
  account — one with transactions — can never be deleted; user gets an unexplained 500.
  *Fix:* migration `f002_account_fk_ondelete` → `ON DELETE SET NULL` on all eleven.
  `finance_transfers.from/to_account_id` are NOT NULL, so they need an explicit app guard
  or `RESTRICT` + a 409.

- [ ] **D2 · Deleting a category 500s when a pending txn or merchant rule points at it**
  `finance.py:1554` clears `FinanceExpense.category_id` / `FinanceIncome.category_id` only.
  It never touches `finance_pending_transactions.category_id` or
  `finance_merchant_rules.category_id` — both populated automatically by Gmail ingestion,
  so this fires without the user creating anything by hand.
  *Fix:* same migration; fix at DB level since ingestion writes outside this router.

- [ ] **D3 · `health_habit_checks` lost its uniqueness and never got it back** [V]
  `alembic/versions/71fb288f8d09:182` drops `uq_habit_check_day`; only the *downgrade*
  recreates it, and no later migration restores it. `app/models/health.py:63` declares no
  `__table_args__`. `api/areas/health.py:453` then reads with `scalar_one_or_none()`.
  A double-tap inserts two rows → **permanent 500 on that habit** until hand-cleaned, and
  streaks silently over-count.
  *Fix:* migration `h016_habit_check_unique` — dedupe, then
  `UniqueConstraint("user_id","habit_id","check_date")` (per-user, not the old global
  pair), mirrored in the model.

- [ ] **D4 · Deleting a user who ever performed an admin action fails**
  `app/models/admin_audit.py:10` — `admin_id` FK with no `ondelete`. Both erasure paths
  skip tables without a literal `user_id` column, so `admin_audit_logs` is never swept,
  and `db.delete(user)` hits the FK and rolls the whole transaction back. This is the
  **GDPR right-to-erasure path**, failing for exactly the accounts most likely to be
  deleted deliberately.
  *Fix:* migration `a002_audit_admin_id_setnull`; store the admin's email in `details` so
  the trail survives.

- [ ] **B6 · Pending-transaction approve takes a raw `dict` with no validation** [V]
  `app/api/finance_pending.py:199` — `data: dict`. Consequences:
  `{"category_id":"nope"}` → uncaught `ValueError` → **500** (should be 422);
  `{"amount":"abc"}` → `InvalidOperation` → 500;
  `{"amount":-5000}` on an expense → `apply_balance(-(-5000))` **increases** the balance
  and writes a negative ledger row, while every other finance create path enforces
  `amount > 0`. `account_id` is never ownership-checked, so an unverified id writes a
  ledger row while the balance silently does not move (endpoint still returns 200).
  📌 *Correction to the sub-audit:* this is **not** a cross-tenant balance mutation —
  `apply_balance` **does** scope by `user_id` (`services/finance/pending.py:49`) [V] and
  no-ops on a foreign account. Severity is "silent data inconsistency + 500s", not
  "tenancy breach".
  *Fix:* a `PendingApprove` BaseModel (`amount: condecimal(gt=0)`, UUID fields,
  `Literal["expense","income"]`, `force: bool`), plus resolve-and-verify the account
  before commit and make `apply_balance` raise rather than warn on a non-None miss.
  `bulk_approve`/`bulk_dismiss` take raw dicts too.

- [ ] **B7 · Web-push endpoint is a blind SSRF primitive**
  `app/api/push.py:31` — `endpoint` is an unvalidated `str`, stored verbatim, and
  `webpush()` makes the server POST to it. Any authenticated user can register
  `http://169.254.169.254/...` or an internal service and trigger any notification path to
  fan out requests from inside the VPC. Blind (responses aren't echoed) but still an
  authenticated internal port-scanner. Nothing caps subscriptions per user either.
  *Fix:* allowlist the four real push-service origins, require https, reject IP-literal
  hosts, cap length and per-user count.

- [ ] **B8 · Admin plan override is a no-op for anyone who has touched the modules UI**
  `app/api/admin.py:110` writes only `plan`/`status`/`addons`, but
  `entitlements.modules_for_subscription` treats `modules` as source of truth and only
  falls back to `plan` when `modules is None`. `set_modules` with billing off writes
  `modules`, so the admin grants "household", the API returns a happy row, and **access
  does not change.** A support tool that lies.
  *Fix:* have `override_plan` also set `modules`/`bundle`, or replace it outright.

- [ ] **B9 · `/api/ai/*` is ungated by `require_module` and mis-gated by `require_plan`**
  `app/main.py:327` mounts `ai_router` with only `_verified`. The webhook sets
  `plan="pro"` whenever **any** module is owned, so a user paying $5 for `finance` alone
  passes `require_plan("pro")` and gets LLM drafting priced under `chat`/`agents`.
  Inversely, a `past_due` user keeps modules via `GRACE_STATUSES` but their AI endpoints
  402 — inconsistent gate semantics on one subscription.
  *Fix:* mount with `Depends(require_module("chat"))` and delete `require_plan` (now its
  only consumer).

- [ ] **B10 · Chat WS accepts an unbounded body straight into the LLM prompt**
  `app/api/chat.py:271` — no length check between `receive_text()` and the provider call;
  Starlette imposes no frame cap. Rate limiting counts *messages* and metering charges a
  flat **1 credit per response** regardless of input size, so 20 × 2 MB frames cost orders
  of magnitude more than 20 credits on the operator's key. Same shape on
  `api/ai.py:120,145` (unbounded `str` fields). `captures.py` gets this right and is the
  model to copy.
  *Fix:* reject `> ~32k chars` with a `too_large` error before the quota check, cap
  attachment bytes, and meter proportional to `usage.input_tokens`.

- [ ] **B11 · Stripe webhook idempotency is check-then-insert, not atomic**
  `services/billing/service.py:293,331` — SELECT then INSERT at the end. Two concurrent
  deliveries (Stripe retries aggressively) both pass the check, both apply, and the second
  mark raises `IntegrityError` → 500 → **Stripe retries forever**.
  *Fix:* insert-first with `ON CONFLICT DO NOTHING`, treat `rowcount == 0` as duplicate.

- [ ] **B12 · `_resolve_category` silently discards an unknown or foreign `category_id`**
  `finance.py:487` returns `(None, None)`; callers then write `"Uncategorized"`.
  `update_expense` will therefore **clear a correctly-set category** when the client sends
  a typo'd UUID, and return 200 — making a client bug look like server data loss.
  *Fix:* 404/422 on a non-existent category id.

# PHASE 2 — Frontend trust surface (target: week 2)

The three items here are what make the product read as "AI slop" rather than software
someone trusts with money and health data.

- [ ] **F1 · 92% of data queries have no error state — a failed API call renders as
      "you have no data"** [V: 151 `useQuery` / 13 `isError`]
  `apps/shell/src/App.tsx:8` sets only `retry`/`staleTime`, no `throwOnError`. Call sites
  default the result (`const { data: goals = [] }`), so a **500 renders the empty state**.
  This is the worst possible failure mode: the user believes their data is gone.
  Confirmed missing on `DashboardPage.tsx:99` (7 queries, 0 handling), `HomeTab.tsx:64`
  (8 queries), `CareerPage.tsx:35`, `ReviewPage.tsx:65`.
  *Fix:* `throwOnError` for route-level queries behind `RouteErrorBoundary`, or adopt the
  in-repo reference pattern — `AgentsPage.tsx:112` and `WeekPlanPage.tsx:94` already
  destructure `isError, refetch` and render the existing `@ledgr/ui` `ErrorState`.

- [ ] **F2 · Form validation feedback does not exist — everything is a toast**
      [V: 166 `<Input>` / 6 `invalid=` / **175** `toast.error`]
  `@ledgr/ui` `Input` supports `invalid` (sets `aria-invalid`, red border —
  `Input.tsx:9`). It is essentially unused. `aria-describedby` appears 4× against 77
  `required` attributes. A toast says *that* it failed, never *which field* — on a
  multi-field dialog the user is guessing. **This is the single loudest AI-generated-app
  tell in the product.**
  *Fix:* validate on blur/submit; pass `invalid` + a `<FieldError id>` wired through
  `aria-describedby`. Reserve toasts for transport errors.

- [ ] **F3 · Install ESLint — `pnpm lint` points at a binary that isn't there** [V]

# PHASE 4 — Scale & consistency (target: week 4+)

Nothing here breaks at 1k rows; all of it degrades badly at 10k.

- [ ] **S1 · Gmail sync loads every stored message on every run** —
  `services/integrations/gmail.py:117` hydrates the full ORM message history *including
  `body_text`* into a dict, every 30 min per linked account. At 50k messages this is
  hundreds of MB and will OOM the worker. *Fix:* `.in_(fetched_ids)` or an upsert.
- [ ] **S2 · Global scheduler jobs load every user and process serially** —
  `services/agents/scheduler.py:96` `select(User)` → sequential loop, no batching, no
  concurrency. At 10k users a 200ms/user job takes ~33 min and APScheduler's default
  `max_instances=1` starts **silently** dropping fires. *Fix:* keyset pagination +
  bounded concurrency + explicit `misfire_grace_time`/`coalesce`.
- [ ] **S3 · Missing indexes on hot paths** — Postgres does not auto-index FKs.
  `health_habit_checks.habit_id` (no index at all, yet the streak query filters on it),
  `health_workout_sets.session_id` (N sequential scans per page load), `health_logs`
  (highest-volume table, `(user_id)` only, every read is a time range — finance got its
  composites in `p001`, health never did), plus `career_events`, `captures`, `briefings`,
  `ai_usage_records`, `tasks.due_date`. *Fix:* migration `p002_hot_path_composites`.
- [ ] **S4 · N+1s and unbounded lists** — `health.py:477` (1 query per session),
  `health.py:895` (2 per routine), `career.py:325` (whole journal for a streak),
  `health.py:368` (every `HabitCheck` ever, per call), workspace projects/sprints/tasks/
  milestones (no limit at all), `admin.py:53` (**no cap** — one request returns every
  user). `insights.py:151` uses `Query(ge=, le=)` correctly and is the model to copy.
- [ ] **S5 · Negative `limit` reaches the DB** — `min(limit, 200)` with no floor →
  `?limit=-1` → Postgres error → 500. Several sites.
- [ ] **S6 · `GET /chat/sessions/{id}` returns the OLDEST 100 messages** —
  `chat.py:62` orders ascending, so any conversation past 100 messages opens at its
  beginning and can never reach the end. The WS history loader 270 lines away does it
  correctly. Also `DELETE` removes messages **one row at a time**.
- [ ] **S7 · Fire-and-forget tasks are unreferenced** — `finance.py:551,620`
  `asyncio.create_task(...)` with no reference held (GC-eligible mid-flight) and
  exceptions never retrieved. `knowledge.py:127` does it correctly — copy that.
- [ ] **S8 · Pick one API convention per dimension and write it into `backend/CLAUDE.md`**
  — status codes (201 vs 200 on create; 204 vs `{"status":"deleted"}` on delete),
  `response_model` (declared in `workspace`/`goals`, absent across all three area
  routers), pagination (`{items,total,has_more}` vs bare arrays vs unbounded), and error
  envelopes (`detail` is a string in some routers and an object in `entitlements.py`, so
  the frontend must handle both).
- [ ] **S9 · Frontend bundle: 889 kB entry / ~410 kB gzip before first paint** — route
  splitting is done well (26 `lazy()`, per-page chunks <82 kB); the weight is all in the
  eager `index` chunk. Not a launch blocker.
- [ ] **S10 · Model metadata disagrees with the DB on `ondelete`** — 4 FKs are `CASCADE`
  in migrations but plain in the models. Tests build SQLite from that metadata, so
  **cascade behaviour under test ≠ production.**
- [ ] **S11 · Only 2 CHECK constraints in 76 tables** — every other enum (account type,
  opportunity status, task status/priority, subscription plan…) is free text validated
  only in Pydantic, which agent and ingestion writers bypass entirely. No amount CHECK
  anywhere.
- [ ] **S12 · Mixed naive/aware timestamps, not domain-aligned** — most tables were
  converted to naive, but `workspace.*`, `career_journal_entries` and `saved_quotes` are
  tz-aware, so the app compares naive and aware values across domains.
- [ ] **S13 · Frontend has one test file** — start with `@ledgr/ui` render tests asserting
  the 32px toolbar contract and the focus ring; that would have caught several documented
  regressions (`Portal`, `KpiGrid`) that were only found by manual browser measurement.
- [ ] **S14 · No GDPR data export** — deletion is thorough; export does not exist
  (Art. 15/20 unsatisfiable without a manual DB query). Legal *pages* exist; the *right*
  doesn't.
- [ ] **S15 · No LLM timeouts or retries** — `tenacity` is a declared dependency and is
  **never imported**. LLM clients are built with no `timeout=`, inheriting the SDK's 10 min
  default, while gunicorn's `--timeout 120` reaps the worker first. A slow provider
  degrades the whole API on a 2-worker box. (Non-LLM integrations *are* correctly bounded
  at 10–30s.)
- [ ] **S16 · Chat WS reconnects forever every 3s regardless of close code** —
  `hooks/useChat.ts:64`. Backend closes `1008` for unauthenticated/unentitled users, so a
  logged-out tab hammers `/ws/chat` indefinitely and a backend outage produces a
  self-inflicted thundering herd on recovery. *Fix:* exponential backoff + inspect the
  close code.
- [ ] **S17 · No soft delete or audit trail on financially significant tables** — zero
  `deleted_at` in the schema. Deleting an expense hard-deletes it *and* mutates
  `finance_accounts.balance` with no record of what was reversed.
- [ ] **S18 · `skip_tests` allows a one-click red-build deploy to production** —
  `.github/workflows/deploy.yml:29`. Intentional, but should at minimum require the
  `production` environment approval the `deploy` job already carries.

## Denormalisation register (things that can silently drift)

No fix required today — but every row here is a place where two sources disagree and
nothing reconciles them. Worth a nightly consistency check before scale.

| Cached value | Truth | Kept in sync by | Breaks when |
|---|---|---|---|
| `finance_accounts.balance` | the ledger | `_adjust_balance` on every write | any direct balance edit (`update_account` deliberately allows one) |
| `finance_goals.current_amount` | `goal_contributions` | inc/dec at write time | `PATCH /goals/{id}` sets it outright, bypassing contributions |
| `finance_expenses.category` (text) | `category_id` | `_resolve_category` | renaming a parent leaves history on the old string |
| `finance_investments.invested_amount` | `investment_transactions` | **nothing** | always — XIRR and the scalar disagree by design |
| `finance_cc_bills.paid_at` | `obligation_payments` | mirrored in one router only | any other path marking it paid |
| `subscriptions.plan`/`addons` | `modules`/`bundle` | `reconcile_subscription` | legacy columns still read by `admin.py`, `/checkout`, `require_plan` |

Also: `finance_obligation_payments.obligation_id` is a **typeless polymorphic id** — no
FK, pointing at bills/loans/cc_bills by an unconstrained `obligation_type` string.
Deleting any obligation leaves paid-state rows forever, and the payables checklist
carries ghosts.

## Sequencing rationale

**Phase 0 before anything else** — B1–B4 are the difference between "an incident is a bad
afternoon" and "an incident ends the company". They are also the cheapest items here.

**T1 before T2** — deleting dead code drops 17% of the token-lint baseline for free.
Re-locking the ratchet first would bake dead code into the bar.

**F3 before F4** — the ESLint install is what makes the `any` ratchet enforceable;
doing F4 first just means it re-accumulates.

**T5's lint rule is the durable half of that item.** Building `IconButton` fixes 14 sites
once; banning `styled.button` under `apps/**` is what stops the 15th.

The through-line across all five audits: **this codebase's problem is not knowledge, it is
enforcement.** The tokens are real, the palette is validated, the layering is clean, the
isolation is genuine — and then `pnpm lint` points at a binary that was never installed,
the ratchet is blind to the dominant drift classes, and the four-state UI contract
(loading/empty/error/invalid) is honoured on two pages out of thirty. Close the gates and
the quality follows; leave them open and every fix in this document re-accumulates.
